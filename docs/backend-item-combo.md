# الكومبو لكل صنف داخل القائمة — العقد بين الباك والداشبورد

> **الحالة:** الباك جاهز على `api-test` (اختبارات القبول الـ ١٤ مغطّاة عنده في
> `tests/Feature/Branch/EachItemCanOfferTheComboOrNotTest.php`). الداشبورد مطابق لهذا العقد.
> **المتبقي:** الموقع (خارج هذا المشروع) يجب أن يخفي خيار الوجبة ويعالج الرمز `combo_not_offered`.

## 1. الفكرة

سعر الكومبو واحد للقائمة (`combo_price`). لكن كل صنف داخل القائمة يُقرَّر له هل يظهر له خيار الوجبة أم لا،
كأن يظهر للساندويتشات فقط دون المشروبات.

## 2. العقد كما نُفِّذ على الباك

### الحقل

`item_menu.has_combo` (boolean، افتراضي `true`). بعد النشر كل الأصناف `true`، فلا يتغير شيء في أي فرع.
حفظ القائمة أو الصنف من الفورم العادي **لا يعيد** `has_combo` إلى `true`.

### القراءة

`has_combo` (boolean دائماً) موجود في كل صنف في:

- `GET /api/menus/{id}` و`GET /api/public/menus/{id}` ← `data.items[]`
- `GET /api/public/categories?branch_id=…` ← أصناف كل تصنيف
- `GET /api/public/branches/{branch}/items/{item}` و`GET /api/public/menus/{menu}/items/{item}` ← صفحة الصنف

أصناف القائمة تأتي بالحقل **`id`** لا `item_id`.

### `meal_price` — نقطة تحتاج قراراً من الباك

الوضع الحالي عند الباك: `meal_price` **غير محسوب**، هو قيمة محفوظة لكل صنف في كل فرع، و`null` تعني أن الصنف لا
يُباع وجبة في هذا الفرع أصلاً. وحين `has_combo = false` يرجع `meal_price = null`، وفي صفحة الصنف يرجع `combo = null`.
وسعر الوجبة المحسوب = `price + combo_price` بشرط أن يكون `meal_price` غير `null`. أي أن الخيار يظهر للصنف إذا
تحققت الثلاثة معاً: للقائمة `combo_price`، و`has_combo = true`، و`meal_price` غير `null`.

**المطلوب:** قرار الأونر هو المفتاح `has_combo` وحده. إن شغّل الكومبو لصنف فيجب أن يظهر له خيار الوجبة، وإن أطفأه
فلا يظهر. فنطلب أن يكون `has_combo` **المتحكم الوحيد**، وألا يمنع `meal_price = null` الوجبة، بل يُحسب سعرها
`price + combo_price`. وإلا حصل أن يشغّل الأونر المفتاح لصنف `meal_price` له `null` فلا يظهر له الخيار عند الزبون
(أو يُرفض الطلب)، والأونر لا يرى سبباً لذلك في الداشبورد لأنه لا يعدّل `meal_price`.

### الحفظ

```
PUT /api/menus/{menu}/items/{item}/combo
{ "has_combo": false }

← 200 { "status": true, "message": "...", "data": { "menu_id": 3, "item_id": 2, "has_combo": false } }
```

- يجوز تكرار القيمة نفسها، ويُحفظ حتى لو لم يكن للقائمة `combo_price`.
- الأخطاء: `401`، و`403` (بلا صلاحية)، و`403 outside_your_branch` (مدير فرع على قائمة فرع غيره)، و`404` (القائمة أو
  الصنف غير موجود، أو الصنف ليس في هذه القائمة)، و`422` مع `errors.has_combo`.

### الصلاحية

`menus.items.combo.update` تحت مجموعة **Menus**. وقت النشر أخذتها تلقائياً **مرة واحدة** كل دور أو شخص معه
`menus.combo.update`. وبعدها إن شالها الأونر من أحد تبقى مشالة.

### قواعد الطلب

طلب `variant: "meal"` لصنف `has_combo = false` يُرفض:

```json
HTTP 422
{
  "code": "combo_not_offered",
  "message": "لا يتوفر كولا كوجبة في هذا الفرع. اطلبه وحده.",
  "data": { "item_id": 2, "item_ids": [2], "menu_id": 3, "order_id": 41 }
}
```

- ينطبق على الموقع (`POST /api/orders/{id}/menu-items`) وعلى **الكاشير** (`POST /api/admin/orders`). الكاشير غير مستثنى.
- عند `POST /api/orders/{id}/submit`: إن انطفى الكومبو لصنف بعد أن وضعه الزبون وجبة في سلته، يرجع الرمز نفسه مع
  `item_ids` (كل الأسطر المعنية).
- طلب `sandwich` للصنف نفسه يُقبل بسعر الصنف وحده. والأصناف `has_combo = true` تسعيرها بلا أي تغيير.

## 3. ما يفعله الداشبورد

| الموضع | السلوك |
|---|---|
| **نموذج تعديل القائمة** | بجانب كل صنف (قرب سعره) خلية «الكومبو» ومفتاح، تُحفظ فور تحريكها بمسارها الخاص ولا تنتظر زر «حفظ» الفورم. تظهر للصنف المحفوظ في القائمة، إن كان للقائمة `combo_price` أكبر من صفر **وأرسل الخادم** `has_combo` للصنف. وصفحة العرض لا تعرض المفتاح. |
| **من يحرّك المفتاح** | من يملك `menus.items.combo.update`، ومدير الفرع على قائمة فرعه فقط. غيرهم يرى «مفعّل/معطّل» نصاً. |
| **الحفظ** | `PUT menus/{menu}/items/{item}/combo` بالجسم `{ "has_combo": bool }`، ويقرأ `data.has_combo` كالحالة المحفوظة. |
| **نقطة البيع** | خيار «وجبة» يُعطَّل إن كان `has_combo = false` فقط. المفتاح هو القرار وحده، والداشبورد لا يفحص `meal_price`. غياب `has_combo` يعني السلوك القديم، فلا يتعطل البيع. |
| **رفض الطلب** | `combo_not_offered`: يعرض الكاشير **رسالة الخادم** (فهي مترجمة وتذكر اسم الصنف)، وإن غابت فنصاً ثابتاً. |
| **الصنف** | يُقرأ بـ`item_id` وإن غاب فـ`id`، فيعمل مع `id` كما يرسله الخادم. |
| **تلميح إعدادات الكومبو** | يذكر أن الاستثناء يكون بمفتاح «الكومبو» بجانب الصنف في نموذج تعديل القائمة. |

الاختبارات: `scripts/tests/item-combo.test.mts` (قراءة `has_combo` و`meal_price` ومنطق الإخفاء).

## 4. ملاحظات للانتباه

1. **الداشبورد لا يعدّل `meal_price` ولا يبني عليه.** يظهر في تفاصيل الصنف للقراءة فقط، والمفتاح `has_combo` هو
   القرار. ولذلك نطلب من الباك أن يكون `has_combo` المتحكم الوحيد (انظر «`meal_price` — نقطة تحتاج قراراً» أعلاه).
2. **الكاشير مقيَّد بالقاعدة نفسها** كالزبون، فلا يبيع وجبة لصنف مستثنى.
3. **ترتيب النشر:** الباك أولاً (تم)، ثم الداشبورد، ثم الموقع.

## 5. للتحقق اليدوي بعد نشر الداشبورد

| # | الخطوة | المتوقع |
|---|---|---|
| 1 | افتح «تعديل» لقائمة لها `combo_price` | تظهر خلية «الكومبو» ومفتاح بجانب كل صنف محفوظ |
| 2 | عطّل مفتاح صنف | رسالة «تم حفظ إعداد الكومبو»، ويبقى معطلاً بعد إعادة تحميل الصفحة |
| 3 | افتح الصنف في نقطة البيع | زر «وجبة» معطّل مع «لا كومبو لهذا الصنف» |
| 4 | افتح قائمة بلا `combo_price` | لا تظهر مفاتيح كومبو |
| 5 | حساب بلا `menus.items.combo.update` | يرى «مفعّل/معطّل» نصاً بلا مفتاح |
| 6 | صنف `has_combo = true` و`meal_price = null` | خيار الوجبة يظهر في نقطة البيع (القرار للمفتاح). تحقّقوا أن الباك يقبل طلبه ويسعّره `price + combo_price` |

## 6. اختياري لاحقاً

سعر كومبو خاص بالصنف: عمود `combo_price` من نوع nullable على العلاقة نفسها، و`null` يعني سعر القائمة. غير مطلوب الآن.
